   - In MovieVerse:

       to load specific movie/anime details.
     * Built `<ProtectedRoute>` to guard private routes and auto-redirect visitors to `/login`.

2. COMPONENT STRUCTURE (Organizing the UI)
   - What we solved: Code was getting disorganized, so we refactored into a scalable structure.
   - In MovieVerse:
     * Restructured `src/member2/` into the professional "Folder-per-Component" and 
       "Folder-per-Page" pattern.
     * Each component folder (like `AnimeCard/`, `MovieSkeletonCard/`, `WatchlistCard2/`, 
       `LoginPage/`, `ProfilePage/`) contains:
       - `.jsx` (the React component logic & UI)
       - `.module.css` (scoped styles to avoid CSS class clashes)
       - `index.js` (clean directory entry point)
     * Created central barrel export files (`src/member2/index.js`, `components/index.js`, 
       `pages/index.js`) so any component can be imported with one clean import statement.

3. CONTEXT API (Sharing data across components)
   - What we solved: Avoided "prop drilling" (passing user info down through 5 levels of props).
   - In MovieVerse:
     * Built `AuthContext.jsx` and `AuthProvider`.
     * It wraps the entire app in `src/main.jsx`.
     * Created a custom hook `useAuthContext.js`.
     * Now any component (like Navbar, Profile, or ProtectedRoute) can get the current user 
       in a single line: `const { user, signOut } = useAuthContext();`

4. STATE ARCHITECTURE (Deciding where data should live)
   - What we solved: Placed state at the right level for speed, persistence, and reliability.
   - In MovieVerse:
     * Local UI state: `useState` for search text, form inputs, loading spinners, and active tabs.
     * Non-rendering mutable state: `useRef` to track `loadingRef`, `seenIds`, and `fetchedPages` 
       in infinite scrolling so rapid scroll events never trigger duplicate requests.
     * Persistent user state: `localStorage` for user login session, saved Watchlist, and Watched history.
     * Session network cache: `sessionStorage` in `tmdbApi.js` to store fetched movie lists for 
       5 minutes, saving internet data and speeding up page loads.

5. REDUX / SHARED & COMPLEX STATE (Centralized cross-component state)
   - What we solved: Keeping cards, modals, page views, and navbar badge counts 100% in sync.
   - In MovieVerse:
     * Centralized state managers in `localAuth.js`, `watchlist2.js`, and `watched2.js`.
     * Built an event-driven broadcast system (`window.dispatchEvent`):
       - When a user clicks "+ Watchlist" or "Mark Watched" anywhere:
       - Events `watchlistUpdated` and `watchedUpdated` are fired.
       - Navbar count pills, hero buttons, card buttons, and profile stats instantly update 
         everywhere at the same moment without needing page refresh.

6. FORM HANDLING (Reading and validating user input)
   - What we solved: Secure user sign-in and sign-up with real-time feedback.

4. TOP 10 VIVA QUESTIONS & READY ANSWERS (MEMORIZE THESE!)
--------------------------------------------------------------------------------

Q1: "Why did you use IntersectionObserver instead of a window scroll event listener?"
A1: "Window scroll events fire dozens of times per second on the main thread, causing lag and 
     choppy scrolling unless debounced. IntersectionObserver runs asynchronously in the browser 
     engine off the main thread. It only notifies us when the bottom sentinel element enters the 
     viewport, which is much better for performance."

Q2: "What is prop drilling and how did you avoid it?"
A2: "Prop drilling is passing data through many intermediate components that don't need it just to 
     reach a deeply nested child. We avoided this by using React's Context API (`AuthContext`). 
     Any component in the tree can directly read the user state using our `useAuthContext()` hook."

Q3: "How does your infinite scroll avoid duplicate movie cards or double requests?"
A3: "We use a 3-layer guard:
     First, a `loadingRef` boolean prevents concurrent fetches during scrolling.
     Second, a `fetchedPages` Set tracks which pages have already been requested.
     Third, a `seenIds` Set filters out any movie ID that is already in the list."

Q4: "What is the difference between useState and useRef in your project?"
A4: "useState is for data that must trigger a re-render when changed, such as the movie list, 
     active tab, or search text. 
     useRef holds mutable values that persist across renders WITHOUT triggering a re-render, 
     which we used for `loadingRef`, `seenIds`, and `AbortController` in infinite scrolling."

Q5: "Why did you normalize the TMDB data?"
A5: "TMDB API returns properties like `poster_path`, `vote_average`, and numeric `genre_ids`. 
     Our MovieVerse UI components expect `image`, `rating`, and `genres` (as string names). 
     By normalizing the data in `tmdbApi.js`, our components stay clean and don't care whether 
     the data came from TMDB or local fallback."

Q6: "How does the app work when the user has no internet connection?"
A6: "In `tmdbApi.js`, all fetch calls are wrapped in a 3-tier try/catch with a 12-second timeout. 
     If the network is down, it catches the error and automatically loads our local `shows.js` data 
     with `{ isFallback: true }`. The UI displays the fallback notice banner so the user experience 
     never breaks."

Q7: "How do the Watchlist and Watched counters in the Navbar update without page reload?"
A7: "We use an event-driven pub-sub architecture. Whenever an item is added or removed, 
     we dispatch a custom window event (`watchlistUpdated` or `watchedUpdated`). 
     The Navbar, cards, and profile components listen to these events with `addEventListener` 
     in a `useEffect` and update their state immediately."

Q8: "Why did you need an HTTP/2 proxy in Vite?"
A8: "TMDB is hosted on AWS CloudFront, which frequently terminates HTTP/1.1 TLS handshakes from 
     certain Indian ISPs with socket hangup errors. By implementing a native Node.js `node:http2` 
     proxy in `vite.config.js`, we establish an ALPN `h2` multiplexed connection that streams data 
     reliably in ~100ms with zero disconnections."

Q9: "Why did you organize files into the Folder-per-Component pattern?"
A9: "It isolates each component's JSX, scoped CSS Module, plain CSS export, and index entry point 
     together in one folder. This eliminates global CSS name collisions, makes components easily 
     portable, and provides clean barrel imports via `index.js`."

Q10: "How does ProtectedRoute work in your application?"
A10: "ProtectedRoute is a wrapper component. It checks the user session from `AuthContext`. 
      If the user is logged in, it renders the child `<Outlet />` or page. 
      If not, it uses React Router's `<Navigate to="/login" replace />` and passes `location` in state 
      so after logging in, the user is redirected right back to the page they originally requested."
